# CodexThreadBridge v0.3 OpeniLink 运行说明

本说明对应 v0.3 当前实现：在 v0.2 Gateway Core 之上，新增真实微信私聊文本 runtime。runtime 采用 iLink/OpenClaw-WeChat 风格的 HTTP 传输形态，负责从 `getupdates` 拉取微信消息、映射成 Gateway 已有的 `IncomingMessage`，再通过 `sendmessage` 把文本回复发回微信。

Gateway Core 的职责没有下放给通道层：alias 绑定、owner 权限、Codex session dispatch、只读状态命令、artifact 安全边界和“无心跳”原则仍由 Gateway Core 持有。OpeniLink runtime 只负责通道轮询、协议映射、文本发送、cursor 与发送状态记录。

## 本地配置

从仓库根目录复制配置模板：

```bash
cp .env.example .env
```

`.env` 只放本机真实配置和 token，已经被 `.gitignore` 排除，不能提交到仓库。`.env.example` 只能保留占位值，不能写入真实 token、真实 owner id 或任何可用密钥。

v0.3 real runtime 必填变量：

```text
CTB_PROJECT_ROOT=/Users/clngs/Documents/CLngs_Vault/CodexThreadBridge
ILINK_BASE_URL=<iLink/OpenClaw-WeChat bot base URL>
ILINK_BOT_TOKEN=<本机 iLink bot token>
ILINK_OWNER_USER_IDS=<owner 微信 sender id，多个用英文逗号分隔>
CTB_CONTROLLER_COMMAND=<cross-thread-controller MCP 启动命令，逗号分隔>
```

说明：

- `CTB_PROJECT_ROOT` 指向 CodexThreadBridge 仓库根目录。
- `ILINK_BASE_URL` 会用于调用 `getupdates` 和 `sendmessage`。
- `ILINK_BOT_TOKEN` 只用于本机请求头鉴权，运行时错误会做脱敏。
- `ILINK_OWNER_USER_IDS` 决定哪些私聊 sender id 有权使用 Gateway。
- `CTB_CONTROLLER_COMMAND` 是逗号分隔的命令数组，例如 `python3,/absolute/path/to/server.py`。不配置时 real runtime 会拒绝启动。

可选变量：

```text
ILINK_POLL_TIMEOUT_SECONDS=35
ILINK_REQUEST_TIMEOUT_SECONDS=30
```

## 启动方式

本仓库采用 `src` layout。如果没有先安装本包，在仓库根目录用 `PYTHONPATH=src` 启动。

先处理一批消息后退出，适合 smoke：

```bash
set -a
source .env
set +a
PYTHONPATH=src python3 -m codex_thread_bridge.adapters.openilink_runtime --once
```

正常常驻运行：

```bash
set -a
source .env
set +a
PYTHONPATH=src python3 -m codex_thread_bridge.adapters.openilink_runtime
```

runtime 会读取 `data/bridge.sqlite3` 中的 Gateway 状态，同时记录 iLink cursor、outbox 和 delivery 状态。通道轮询只是读取微信侧更新，不是 Codex heartbeat，不会主动向 Codex session 发送“检查在线”“汇报状态”之类模型 turn。

## 微信私聊 smoke

在 owner 私聊里按顺序发送：

```text
/help
/list
/add code <session_id>
/use code
请只回复 bridge real runtime ok
```

期望行为：

- `/help` 返回 Gateway 支持的命令说明。
- `/list` 返回当前 alias 列表；没有 alias 时也不创建模型 turn。
- `/add code <session_id>` 通过 controller 读取目标 Codex session 状态，并保存 `code` alias。
- `/use code` 把当前私聊上下文切到 `code`。
- `请只回复 bridge real runtime ok` 会作为普通私聊文本发给当前 alias 对应的 Codex session，并把 Codex 返回文本通过 iLink `sendmessage` 发回微信。

## 安全边界

- v0.3 只启用微信私聊文本 runtime。
- 非 owner sender id 会被 Gateway 拒绝，不能绑定 alias 或 dispatch Codex。
- 群聊 QA runtime 不在 v0.3 启用；iLink 群消息会被 runtime 忽略。
- 私聊里的 `/group ...` 管理命令会被 runtime 直接拦截，并返回“Group QA runtime is not enabled in v0.3.”，不会进入 Gateway。
- 文件上传和文件发送不在 v0.3 启用；iLink client 的 file upload 仍是未实现边界。
- `/list`、`/status`、`/refresh` 只读本地/Gateway/controller 状态，不创建 Codex 模型 turn。
- channel polling 不是 Codex heartbeat；runtime 轮询微信通道不代表向 Codex 发消息。
- Codex 工具审批仍在 Codex App 内完成，微信侧不代理 approval confirmation。
- Gateway Core 仍然持有 alias、权限、Codex dispatch 和 artifact safety gate；通道层不绕过这些边界。

## 发送语义

v0.3 使用本地 outbox 降低重复执行风险。runtime 在调用 Gateway 后，会先把待发送回复写入 `runtime_state` 的 `ilink.outbox.<message_id>`，再调用 iLink `sendmessage`。如果 `sendmessage` 失败并重试，同一个微信消息会复用本地 outbox 中的回复文本，不会再次运行 Gateway 或再次创建 Codex turn。

如果进程在“已经标记为 sending、但无法确认远端是否收到回复”的窗口崩溃，下一次处理同一消息时会记录 `delivery_unknown`，把该消息标记为已处理，并把 delivery 状态置为 `unknown`。这个策略偏向避免重复远端回复；代价是少数崩溃窗口内可能需要人工根据微信侧实际情况判断是否补发。
