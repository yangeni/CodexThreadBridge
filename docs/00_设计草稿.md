## 1. 设计目标

CodexThreadBridge 的目标不是重新做一个 Agent，而是做一个本机线程网关：

```text
手机聊天软件
-> Channel Adapter
-> Local Gateway
-> Binding Store
-> cross-thread-controller MCP
-> Codex history session
```

它要解决的问题是：用户可以在手机聊天软件中，把某个聊天上下文绑定到一个已有 Codex 历史线程，然后通过手机继续向该线程发送消息，并把 Codex 的结果回传到手机。

第一版只追求稳定地接入已有线程，不追求自动实时同步 Codex App UI，也不追求微信、QQ、飞书三端一次性全部完成。

## 2. 核心判断

这里区分两个不同层次：

```text
直接映射：
聊天上下文 -> 目标 Codex session

中介线程：
聊天上下文 -> 调度线程 -> 目标 Codex session
```

本工程采用混合模式：

- 未绑定时，Gateway 负责解释 `/bind`、`/status`、`/help` 等入口命令。
- 已绑定后，普通消息直接进入目标 Codex session。
- 中介线程只作为后续高级能力保留，例如自然语言查找线程、选择目标、确认高风险动作；它不长期夹在每条消息中间。

这样可以保留自由度，同时避免每条消息多消耗一层模型额度。

## 3. 不做模型心跳

后台刷新必须遵守一个硬规则：

```text
后台同步只能读本地状态，不能主动向 Codex session 发送心跳式模型消息。
```

允许的低成本操作：

- 读取 binding SQLite。
- 读取 controller status。
- 读取 Codex session JSONL。
- 比较 `session_head`。
- 手动 `/refresh` 时提取新增消息。

禁止的操作：

- 定时发送“你在吗”。
- 定时发送“汇报当前状态”。
- 为了检查线程是否活着而创建新 Codex turn。

## 4. 线程控制模型

Gateway 不直接操作 Codex App UI，而是调用 `cross-thread-controller` MCP。

手机发起消息时，固定流程是：

```text
status
-> start 或 send
-> wait_any
-> read_result
-> delivery_ack
-> close
-> release
```

关键约束：

- 如果目标 session 被其他 active owner 锁住，Gateway 不抢锁。
- 如果 `dirty=true` 或 `reconcile_required=true`，Gateway 停止写入并提示处理。
- 如果 `expected_session_head` 与真实 head 不一致，Gateway 停止写入并提示 `/refresh`。
- `force_recover`、跨 owner 接管、写权限执行都必须有明确确认。

## 5. 数据模型草案

Binding Store 使用 SQLite。

```text
bindings
- id
- platform
- chat_id
- thread_key
- bound_session_id
- alias
- last_seen_session_head
- mode
- owner
- created_at
- updated_at
```

字段含义：

- `platform`：`local`、`feishu`、`qq`、`wechat`。
- `chat_id`：平台会话 ID。
- `thread_key`：平台里的子线程、话题或消息根 ID；没有就等于 `chat_id`。
- `bound_session_id`：Codex session id。
- `alias`：用户给绑定起的短名。
- `last_seen_session_head`：Gateway 已同步到的 Codex head。
- `mode`：第一版固定为 `direct`，后续可扩展为 `dispatcher`。
- `owner`：Gateway 在 controller 中使用的 owner 名。

Attachment Store 也使用 SQLite，同时文件落盘到 `data/attachments/`。

```text
attachments
- id
- platform
- chat_id
- thread_key
- message_id
- bound_session_id
- original_name
- mime_type
- local_path
- created_at
```

第一版图片不做真正多模态输入，只把本地路径和用户文本一起转发给 Codex。

## 6. 命令协议

第一版支持这些命令：

```text
/bind <session_id>
/unbind
/status
/refresh
/send <session_id> <message>
/help
```

普通消息规则：

- 如果当前聊天已绑定 session，则普通文本直接发送到目标 session。
- 如果没有绑定，则普通文本不自动创建线程，返回 `/bind` 引导。
- 如果消息包含图片，先保存图片，再把路径附在发送文本中。

图片转发文本格式草案：

```text
用户消息：
{text}

附带图片：
- {absolute_local_path}

说明：图片已由 CodexThreadBridge 保存到本地路径；如需要分析图片，请读取该路径。
```

## 7. 安全原则

默认安全策略：

- 只允许白名单用户。
- 默认 `sandbox=read-only`。
- 默认 `approval_policy=never`。
- 不把平台 token、内部 traceback、完整本地敏感路径主动回传到群聊。
- 高风险动作必须二次确认。

高风险动作包括：

- 写文件。
- 执行命令。
- `force_recover` active lock。
- 转移 owner。
- 发送附件到第三方服务。
- 绑定或切换到敏感 session。

## 8. 平台路线

第一阶段：

- `local` 模拟 adapter：命令行或本地 HTTP 方式模拟聊天事件。
- `feishu` adapter：接飞书私聊和群 thread。

后续阶段：

- `qq` adapter：走官方 QQ Bot 能力，线程语义由 Gateway 自己模拟。
- `wechat` adapter：优先考虑官方或低风险方案，不把个人微信号逆向 hook 作为默认路线。

## 9. 成功标准

MVP 成功标准：

- 可以把一个本地模拟聊天上下文绑定到已有 Codex session。
- 普通文本能进入该 session，并把完整回复返回模拟入口。
- 结果处理后 controller session 状态为 `released`。
- `/status` 和 `/refresh` 不触发模型调用。
- 图片能保存到 `data/attachments/`，并以本地路径形式转发给目标线程。
