# CodexThreadBridge v0.2 运行说明

本说明对应 v0.2 当前实现：WeChat-first mobile Agent console、本地模拟器、OpeniLink 微信入口边界、owner 私聊 alias dispatch、群聊隔离 QA，以及 artifact safety gate。

## 本地模拟器

本仓库采用 src layout。包已经安装到当前 Python 环境后，可以直接运行：

```bash
python3 -m codex_thread_bridge.adapters.local --project-root /Users/clngs/Documents/CLngs_Vault/CodexThreadBridge
```

如果尚未安装包，在仓库根目录用 `PYTHONPATH=src` 运行：

```bash
PYTHONPATH=src python3 -m codex_thread_bridge.adapters.local --project-root /Users/clngs/Documents/CLngs_Vault/CodexThreadBridge
```

本地模拟器从 stdin 读取消息，使用内置 EchoController，不会真正调用 Codex。私聊 smoke commands：

```text
/add code <session_id>
/use code
请只回复 bridge smoke ok
```

期望行为：

```text
/add code 019-code       -> Added alias code -> 019-code
/use code                -> Using alias code
请只回复 bridge smoke ok  -> LOCAL: 请只回复 bridge smoke ok
```

模拟群聊时可加 `--conversation-type group`。群聊消息需要以 `@Bot` 开头才会被 Gateway 处理；未批准群会进入 pending 状态并提示 owner 到私聊批准。

## 微信入口

v0.2 的微信入口是 OpeniLink Hub WebSocket inbound。OpeniLink 侧负责接收微信消息，Gateway 只接收 normalized events，不在 Gateway Core 内写微信协议细节。

入口链路：

```text
OpeniLink Hub WebSocket inbound
-> OpeniLink adapter normalize_openilink_event
-> Gateway normalized IncomingMessage
-> Gateway Core routing / policy / store / controller boundary
-> ChannelPort send_text 或 send_file
```

`WeChatChannelPort` 是 Gateway 对微信通道的最小端口：`iter_messages`、`download_attachment`、`send_text`、`send_file`、`send_typing`。OpeniLink adapter 实现这个边界，并把 outbound reply/file sends 转交给具体 OpeniLink client。

## 私聊工作流

owner 私聊是唯一可以 dispatch work aliases 的入口。

```text
/add code <session_id>   读取 controller status，保存 alias、workspace/cwd 和默认执行策略。
/use code                设置当前私聊上下文的 active alias。
普通消息                 发送到 active alias 对应的现有 Codex session。
/list                    列出 alias，不创建模型 turn。
/status [alias]          读取 controller status，不创建模型 turn。
/refresh [alias]         只读本地历史设计边界，不允许用模型补救。
/artifacts [alias]       查看最近一次 run 检测到的 artifact。
/sendfile <id|all>       仅发送 allowed artifact。
```

私聊 work alias 使用目标 session 的 workspace/cwd，默认 `sandbox=workspace-write`、`approval_policy=on-request`，由 Codex/controller 继续承担实际审批边界。

## 群聊 QA

群聊不是工作调度入口。群消息必须显式提及 `@Bot`，并且所在群必须先由 owner 在私聊中批准：

```text
/group approve <group_id> [group_alias]
```

批准后，Gateway 创建或记录该群专用 QA session。群 QA 使用 `sandbox=read-only`、`approval_policy=never`，owner 标记为 `ctb-group-qa:<group_alias>`，用于回答项目问题，不用于执行工作任务。

群内可用：

```text
@Bot 普通问题
@Bot /qa status
```

群内普通聊天如果没有 `@Bot`，会被忽略，不创建 pending 记录，也不调用 controller。

## 安全边界

- 私聊可以 dispatch work aliases；群聊不能 dispatch work aliases。
- 群聊不能 approve actions，批准只能从 owner 私聊发起。
- 群聊不能 reset itself，reset/disable 只能从 owner 私聊发起。
- 群聊不能 receive local files，artifact/file delivery 只允许 owner 私聊。
- `/status`、`/refresh`、`/list`、`/group list`、`/group status`、`@Bot /qa status` 不创建模型 turn。
- 无心跳：后台或状态检查不能发送“你还在吗”“汇报状态”等模型消息。
- artifact 发送前必须通过本地安全检查：路径必须存在且位于允许 roots 内，不能命中敏感路径标记，不能早于 run start，不能超过大小限制。
- OpeniLink 只作为通道边界；Gateway Core 不依赖 OpeniLink 内部实现，也不把平台 token、traceback 或本地敏感路径主动回传到群聊。

## v0.2 不交付项

Feishu 和 Windows 是后续 adapter/packaging targets，不是 v0.2 deliverables。v0.2 的交付面是本机 Python Gateway、本地模拟器、OpeniLink-compatible WeChat channel boundary、alias-based private dispatch、approved group read-only QA、artifact gating 和测试覆盖。
